# Audit Log

The audit log records important state changes in Trustpoint. It is intended for traceability and operational review, not for storing secrets or full request payloads.

Access: **Management > Audit Log**

## Signed exports

Apply the audit log filters, choose **Signed export**, and select an active
traceability credential. Exporting requires both **View audit log** and
**Manage Traceability Credentials** permissions. Each export uses the selected
credential; there is no automatic background signing.

The download contains all matching entries, independent of the current page,
in timestamp and entry-ID order. Exports are limited to 10,000 entries; narrow
the filters for larger logs. The signed payload includes the context
`trustpoint:audit-log:v1`, export time, filters, entry range and count, event
contents, and signing-generation metadata. Signing failures return an error
instead of an unsigned download. Crypto audit events generated by the signing
operation are outside the exported snapshot.

### JWS format

Exports use [RFC 7515 flattened JWS JSON serialization](https://www.rfc-editor.org/rfc/rfc7515.html#section-7.2.2)
with the fields `protected`, `payload`, and `signature`. Each field is an
unpadded base64url string. The protected header contains:

- `alg`: `ES256` for P-256 or `ES384` for P-384.
- `cty`: `application/json`.
- `x5c`: the self-signed generation certificate as a one-element array of
  standard Base64-encoded DER certificates, as defined in
  [RFC 7515 section 4.1.6](https://www.rfc-editor.org/rfc/rfc7515.html#section-4.1.6).

The signing input is the ASCII string `protected + "." + payload`. The
signature is the fixed-width `R || S` encoding defined by
[RFC 7518 section 3.4](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.4):
64 bytes for ES256 and 96 bytes for ES384 before base64url encoding.
The payload contains UTF-8 JSON. Verification uses its exact encoded bytes;
JSON canonicalization is neither needed nor claimed. The response media type
is `application/jose+json`.

The verifier supports this audit-export profile only: all header parameters
must be protected, the certificate must match the independently pinned,
self-signed generation certificate, and the algorithm must match its curve.
Unprotected headers, unknown critical extensions, and unencoded payloads are
not accepted. It does not build certificate paths to arbitrary CA trust stores.
The previous custom export format is not supported; download a new export.

Verify on another machine with Python and `cryptography` installed:

```bash
python -I trustpoint/util/audit_log_export.py trustpoint-audit-log.json \
    --trusted-certificate trusted-generation.pem
```

Obtain the signing-generation certificate independently from a trusted
administrator and check its SHA-256 fingerprint against the traceability
credential's generation history. Do not establish trust using only the
certificate embedded in an untrusted export. Retain trusted certificates for
older generations: verification uses the exact historical certificate and does
not require the Trustpoint database or a currently active, unexpired credential.

The command exits successfully only when the trusted certificate matches and
the payload signature verifies. Editing, removing, or reordering exported
entries invalidates the signature. This protects the exported snapshot; it
cannot detect records deleted before export or prove that the selected source
records were complete. Continuous log protection and external checkpoints are
outside this feature.

## What is recorded

Each audit log entry contains:

| Field | Description |
|---|---|
| Timestamp | Time when the event was recorded. |
| Operation | Type of change or security-relevant action. |
| Target Type | Object type affected by the action. |
| Target | Human-readable object label captured at the time of the action. |
| Actor | User who triggered the action, or `System` for automated actions. |
| Details | Optional structured metadata.  |

The target label is preserved even if the original object is later deleted.

## Operations

Trustpoint records audit events for changes such as:

- credential issuance, renewal, revocation, and deletion
- device, domain, CA, signer, and user changes
- security configuration changes
- TLS certificate changes
- signing operations
- crypto backend operations such as key generation, signing, verification, and key destruction

## Writing audit events

Each business operation has one audit owner: the view, API handler, or service
that coordinates the complete operation. Replace an existing audit call when
adopting a helper for the same event. Model saves and signals do not independently
write security-change events.

For registered security-sensitive objects, use
`management.security_change_audit.security_change(target=instance, actor=user)`
around the complete update, including related-object changes. The scope reads the
original database state, waits for all saves to finish, and writes one entry with
the final persisted differences. Unchanged submissions produce no entry. Changes
and their audit entry share a transaction; an audit write failure rolls back the
change. Use `action='deleted'` for deletion to retain the original object identity.

For creation, call `audit_security_change(target=instance, actor=user, before=None,
action='created')` after saving, within the same transaction. Import forms that
persist during validation require a transaction around validation as well.
Backend setup uses `provider_configuration_changes(actor=user_or_none)` to capture
one event per changed configuration object, including initialization and removal;
nested setup scopes share the outer audit owner.

The helpers select object-specific operations, preserve the actor, and redact
sensitive configuration references. Domain certificate-profile assignments and
truststore certificate membership are included in their parent object's event.
Do not additionally audit each through-model save for those operations.
Distinct business events, such as credential issuance and crypto signing, retain
their dedicated operation types and owners.

`MODEL_CREATED`, `MODEL_UPDATED`, and `MODEL_DELETED` remain available as legacy
filter choices for historical rows. New production writers use specific types.
Existing audit history is preserved by the operation-choice migration.
